## 2026-10-23 - DMNC-1605 dialog chrome fixes + contracts CLI

Brief: `plans/2026-10-23-002-brief-dialog-chrome-fixes.md` (DMNC-1605, DMNC-1572 follow-up). Base: origin/main at f2b5975.

**Item 1, head-end control inset (VOLATILE):**
- **Cause:** both strips have `padding: 4px 12px` (spacing-1 / spacing-3). A 36px IconButton overhangs the 4px block padding (`margin-block: -4px`), so it spans the whole strip and touches the top border; but the inline-end overhang was only 8px (`-spacing-2`, DosDialog on the last end IconButton, DosWindow on the controls container), leaving 12 - 8 = 4px to the right border. IconButton itself has `margin: 0`; it was not the cause. The 0.41.0 CHANGELOG note ("IconButton placement follow-ups") intended an overhang that matched the two strips to each other, not one that was symmetric within a strip.
- **Rule chosen: dock flush, offset 0 on every edge.** The last end IconButton overhangs the full inline-end padding (`margin-inline-end: calc(-1 * var(--spacing-3, 12px))`), so it sits 0px from the top border, 0px from the right border and 0px from the rule. Rejected: equal 4px inset, which needs a 45px strip whenever a control is present (Modal, Lightbox and DosWindow with controls would be 8px taller than Card/DosFigure strips without one). Flush keeps every strip at 37px and is the smallest change.
- **Shared, not per consumer:** the same two rules in `DosDialog.css` (`.eidotter-dialog__end > .eidotter-icon-button[:last-child]`) and `DosWindow.css` (`.eidotter-window__controls > .eidotter-icon-button[:last-child]`). ## 2026-10-23 - DMNC-1609 useTextScramble SSR

Inline brief (Linear DMNC-1609). Base: origin/main at 0a79030.

- **Approach: state initialiser = target text, scramble in a post-mount effect** (no mounted flag). `useState(targetText)`; no `Math.random()` or `prefersReducedMotion()` during render. The effect checks `enabled`/reduced motion, then sets the first scrambled frame and `isScrambling: true`, then runs the rAF loop as before. A mounted flag was not needed: the effect itself is the "after mount" boundary, and keeping the state initialiser deterministic is enough for hydration.
- **Layout effect on the client (judgement call):** the effect is `useLayoutEffect` when `window` exists, `useEffect` otherwise (local `useClientLayoutEffect`, no new export). With a plain `useEffect`, a client-only mount (no SSR) could paint the final text for one frame before the scramble swaps in, a regression against todo 026 (the old initial-frame contract). The layout effect runs after mount/hydration commit but before paint, so hydration still sees the target text and client-only mounts still open on glyphs. Swappable to plain `useEffect` with no test changes if a consumer objects.
- **Behaviour change (minor):** when `targetText` changes (Stat value update), the first scrambled frame now appears immediately instead of after the first `speed` ms tick. `delay` still shows glyphs during the wait, as before.
