## 2026-11-21 - DMNC-1643 PR E: dos-86 becomes the default theme

**What a page that sets no `data-theme` gets (decided: unchanged).** Two layers, as PR D found: the bare `:root` of `tokens.css`, and the theme rule applied by `data-theme`. The bare `:root` is neither Pure Amber nor dos-86 (amber primitives, `text-primary` = #B87C1A, a mix of amber and honest functional roles), before and after this PR. Making no-attribute pages render dos-86 would need either changing the base tokens (which every other theme builds on, plus the Tailwind preset, Swift and Figma outputs) or a `:root:not([data-theme])` rule, which breaks themes set on an element below `<html>` (their undeclared roles would inherit dos-86's resolved values, so Pure Amber on `<body>` would change). The conservative choice: the default changes where it has always applied, through `data-theme`; the bare `:root` stays byte-identical (fixture `root`, plus a dist test that the bundled `:root` ground is still #020003); the migration file says so in its own section.

## 2026-11-21 - DMNC-1643 PR F: the typeface under dos-86

Brief: PR F of the DMNC-1643 plan, inline from the orchestrator. Base: origin/main after PRs A, C, D; rebased onto main after PR B (#596) merged mid-task (no conflicts; generated token files rebuilt).

**Typography map (found first):**
- Tokens: `web.tokens.json` `typography.fontFamily.primary` (Perfect DOS VGA 437, monospace), `body` (JetBrains Mono Nerd Font, monospace), `fallback` (monospace). They are emitted only into `tokens.css` `:root` (+ tokens.js/json). Theme builds use base + theme tokens only, so no theme set a family before this PR.
- Tailwind preset: `fontFamily.dos` / `dos-body` / `dos-fallback` were **literal stacks**, not `var()` references. So `font-dos` (used in TSX by 42 shipped files / ~60 class lists: Button, Badge, Tag, Input, Select, Tabs, Alert, Notification, Stat, Gauge, the health family, Chat, TimelineFeed/TimelinePage, Header root, ...) did not read `--typography-font-family-primary` at all; a token change alone could not move them.
- Component CSS: 22 declarations read `var(--typography-font-family-primary)` (Nav, HeaderButton, DisplayMenu, DosWindow and DosDialog containers, DosFigure, Select popover, PageShell title and section title, LegalPage root, Timeline cards/rails, Terminal, CommandPrompt, Header skip link); Bench (note, label) and `dos-utilities.css` `.dos-body*`/`.dos-caption`/`.dos-micro` read `--typography-font-family-body`; `.dos-page/.dos-hero/.dos-h1-5/.dos-label/.dos-code` read primary. Many children use `font: inherit` / `font-family: inherit` (DosDialog title, Bench title, Tabs, FilterBar, ...).
- No global h1-h6 rule sets a family (eidotter/styles sets no fonts since 0.41); headings take their family from their component.

**What was built (the brief's token split, plus one bridge):**
- New token `typography.fontFamily.heading` (literal display stack, not a reference to primary, so a theme that moves primary cannot drag headings along) and Tailwind `font-dos-heading`.
- **Bridge, needed because of the literal preset:** the preset generator now emits `font-dos` and `font-dos-heading` as `var(--typography-font-family-<name>, "Perfect DOS VGA 437", monospace)`. Without tokens.css the fallback is the old literal stack. Consumer-visible side effect: a consumer who overrides `--typography-font-family-primary` now sees `font-dos` follow it (logged in CHANGELOG under Changed). `font-dos-body` / `font-dos-fallback` stay literal (no theme remaps them).
- `theme.dos-86.tokens.json` sets `typography.fontFamily.primary` to the string `var(--typography-font-family-body)`. A token alias was impossible (theme builds do not load web.tokens.json); the var also keeps a consumer's body-family override in effect. Note: Style Dictionary parses `{...}` inside `$description` as a reference, so the description avoids braces.
- Heading family users (guard: `src/styles/heading-family.test.ts`, `file:line` allowlist with reasons, stale check): `.dos-hero`/`.dos-h1`-`.dos-h5`; SectionHeading; PageShell title; PageSection title; DosWindow and DosDialog strip lead (marker + title; Card, Bench, DosFigure, Modal, Lightbox, CmdPalette titles inherit it); LegalPage h1/h2; TimelinePage year h2 and entry h3; Stat, Gauge and VitalsStrip values; Wordmark (BrandLockup composes it); Header brand link; Terminal and CommandPrompt (bitmap).
- Terminal and CommandPrompt: rather than switching their own declarations, their root redefines `--typography-font-family-primary: var(--typography-font-family-heading)`, so everything inside (Chat components with `font-dos` inside a Terminal, the prompt input) keeps the bitmap face under dos-86 too. Under every other theme the two families are the same stack, so this is a no-op.

**Deviations and conservative choices:**
- **`.dos-page` stays on the primary family** although the brief lists it among the heading-family selectors. It is the page shell for raw prose (its own font size is the text-md body step), so putting it on the heading family would keep all unclassed body copy in the display face under dos-86, against Dom's decision ("JetBrains Mono everywhere except headings"). `.dos-label` and `.dos-code` stay on primary too. Headings inside `.dos-page` that use `.dos-h*` are display; a bare `<h2>` inside `.dos-page` without a class follows the page (body under dos-86). Flip `.dos-page` into the heading block in `dos-utilities.css` if Dom wants the brief's reading.
- **DosWindow / DosDialog strip titles and the Header brand** are not h1-h6 (the window title is a span) but are on the heading family because the brief names them (strip titles, brand lockup). DosDialog's title is an h2 anyway.

- **Serialization:** where the old family came through a literal (`font-dos`) or a `var(primary)` without the fallback var, the new heading declaration also omits `var(--typography-font-family-fallback)`, so the computed `font-family` string under Pure Amber is identical, not just the rendered face (a first pass produced `"Perfect DOS VGA 437", monospace, monospace` in Header, LegalPage, TimelinePage and VitalsStrip; fixed).

Picked by the brief's order (sharp, nothing interactive breaks, then scroll): **SVG filter on the html element**. backdrop-filter failed sharpness (Chromium mixes the blurred layer at its opacity instead of screening it: glyph core luminance -58%). The SVG filter on body breaks `position: fixed` (dialogs and a fixed bar pinned to the document), which is why the filter goes on the root element, the one element the spec exempts. **Decisions and deviations:**
- **Decision record location.** The brief said `ideation/2026-11-21-sampled-glow-spike.md`, committed. `ideation/` is gitignored in this public repo under "Internal/personal files (not for public)". Rather than force-add into a path the repo marks not-for-public, the record is committed as `solutions/tooling-decisions/sampled-glow-technique-2026-11-21.md` (same content plus solutions frontmatter); a local copy stays at the ideation path. The content has no local paths or other project names.
- **Performance is the open risk.** Only SwiftShader (software GL) exists in this environment, headless and headed. There the filter cuts a 5 s scripted scroll on the long page to about a fifth of the frames (about 250 of 300 dropped vs about 30-60 without). Shipped anyway because the brief ranks scroll third and the prop is opt-in, default off; the record asks Dom to check real hardware (Chrome and Safari) before a site opts in. WebKit is not installed: Safari not measured. Firefox not measured.
- **Screen, not add.** The plan says "composited back with screen"; the DOS-86 shader adds. Followed the plan (two `feBlend mode="screen"`); on a dark ground the two are nearly the same and screen cannot clip to white.
- **Radius mapping.** The shader's radius is a ring-sample radius; used as the Gaussian standard deviation (SVG `stdDeviation`, CSS `blur()`), and as 2 x radius for `text-shadow` blur in the baseline (a shadow blur is two standard deviations).
- **New tokens** `effect.phosphor.sampled-{tight,halo}-{radius,intensity}` (1.6px / 0.35 / 4.5px / 0.22), shared `effect.*` (they also reach Swift and the terminal JSON `effects` block, as PR A's tokens did), plus the same four in `effect.preset.long-reading.phosphor`. Defaults equal the preset values: the reference has no other value and the mode is opt-in.
- **Light grounds off.** A screen glow lightens dark ink, so `light` and `amber-paper` (attribute and class selectors) set both strengths to 0 on the overlay root, and the component treats two zero strengths as "element path". This names two theme slugs in `RetroEffects.css` (not in the theme token files, which PR D owns); a new light theme must be added there. VOLATILE.
- **Element glows untouched.** With `sampled` on, the components' own glows (heading `text-shadow`, `shadow-dos-glow*`) still render, so headings get both. Turning them off under sampled glow is a design call for PR E. Not done here.
- **Literal guard allowlist moved, not extended.** The long-reading preset block gained four lines, so the two existing entries moved from :233 / :257 to :237 / :261 (comment in the test says so). No new literal: the new rules use only 0 and tokens.
- **One per page, but overlap-safe.** The filter has a fixed id (`eidotter-retro-glow-filter`) because the CSS rule names it; two sampled instances render duplicate (identical) filters. The html attribute is reference-counted across instances (module-level count), so a route change that mounts the new overlay before unmounting the old one keeps the glow.

- **Re-evaluation** on preference changes (matchMedia `change`), on html `data-theme` / `class` / `data-effects` / `style` changes (MutationObserver) and on `preset`. A theme set on an ancestor other than html is read at mount and on those triggers only.
- **Knowledge base.** The canonical principles page was reachable on this machine; the principle was added there too (with a log entry), uncommitted in that repo, outside this PR.
- Registry changelog line not added (needs a release version; no version bump here), as in PR A.
